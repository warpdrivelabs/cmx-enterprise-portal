架构优势

  • 门户管理能力齐全，已经形成 Shell、导航、工作区、属性面板、日志面板、菜单管理、页面承载等完整前端平台结构。
  • 与 packages/cmx-data-comp、packages/cmx-ui5-runtime 共享封装，符合“复用优先”的工程方向。

架构隐患

  • Native Pages 运行时允许动态 HTML 与脚本执行，能力强但安全边界敏感，必须强化来源可信、沙箱、权限与审计策略。
  • Legacy Node 后端已停用但仍残留在 package.json 脚本中，且 lint 脚本引用不存在目录，说明迁移后清理不彻底。
  • 部分组件过大，业务状态、DOM 拼接、API 调用、交互逻辑混合在单文件内，长期会拖慢迭代和代码审查。

五、性能与体积评估

生产构建成功，但产物体积偏大，Vite 明确提示多个 chunk 超过 1500 kB。当前 dist/assets 中 JS/CSS 合计约 21.7 MB，超过 1.5 MB 的资源 3 个。

资源大小风险
vendor-ignite-spreadsheet-*.js约 5.9 MB电子表格/SpreadJS 类能力重，若首屏加载会显著影响启动时间。
index-*.js约 5.7 MB业务主包偏大，说明部分重型页面或依赖未充分延迟加载。
vendor-ignite-*.js约 2.4 MBIgnite 组件库体积高，应确保只在需要的页面动态加载。
vendor-shiki-*.js约 1.4 MB代码高亮可考虑按需加载或弱化首屏依赖。

优化建议

  • 将定义中心、弹性组合、HTML 预览、Spreadsheet、AI 工作台等重功能按路由/工作区视图动态导入。
  • 检查 cmx-data-comp 导入路径，避免因顶层 barrel export 拉入过多组件。
  • 为 Vite 配置更明确的 manualChunks，把 UI5、Ignite、Shiki、Markdown、Grid 等重依赖分包，并配合懒加载。
  • 建立构建体积预算，例如主入口 gzip 不超过指定阈值，超过则 CI 警告或阻断。

七、主要问题与优先级

优先级问题影响建议动作
P0Native Pages 动态 HTML/脚本执行触发安全红线潜在 XSS、代码注入、权限逃逸风险；同时阻断源码级 ESLint。明确 native page 信任模型；优先使用 iframe sandbox；对片段路径引入 Sanitizer/白名单；必须执行脚本时做显式豁免和安全设计文档。
P0npm run lint 脚本不可用团队无法用标准命令获得质量门禁。移除不存在的 cmx-node-server/**/*.js 模式，或改为 --no-error-on-unmatched-pattern，并确保 CI 使用同一命令。
P1构建产物体积过大首屏慢、缓存压力大、弱网体验差。按工作区视图动态导入重模块；拆分 Ignite/Spreadsheet/Shiki；建立 bundle 预算。
P1核心组件文件超过 4000 行维护难、回归风险高、多人协作冲突多。拆分 portal-flexible-combination-manager.js 与 portal-definition-manager.js，抽出 API、状态机、表单构建、对话框、校验逻辑。
P1Legacy 后端脚本残留迁移边界不清，工具链误报。将 legacy 脚本移入独立文档或显式归档目录；正常开发脚本只保留当前前端职责。
P2缺少自动化 UI 回归信号复杂工作区交互容易出现视觉/布局退化。为登录、主 Shell、菜单管理、定义中心、弹性组合、Native Pages 增加 Playwright 冒烟截图。
